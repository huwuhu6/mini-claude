### 2.1 为什么直接累计 Results 中的 `governance_class` 会错

原始 Baseline 的持久化旧字段分布是 `TP=8, TN=14, FN=7, UNCLASSIFIED=7`；Candidate 的原始旧字段是 `TP=9, TN=15, FN=9, UNCLASSIFIED=3`。如果机械按这些字段计算，与后期报告的 `11/18→13/18` 不一致。**这不是发现报告捏造数字，而是评分口径随版本演进发生了变化**。当时的审计脚本 `scripts/audit_anti_loop_accounting.py` 使用 `grade_trial()` 从原始 Case 合同、Result 和独立 Trace 重新评分，而不是累加旧的缓存分类。其相关实现位于 `src/core/evaluation/anti_loop.py`：对于 must-stop，最终 `BLOCKED_ENVIRONMENT` 或 `CIRCUIT_BROKEN` 且没有 Runtime Error 时，归为可观察的 STOP；其它未能观察到 STOP 的必须按 FN 进入分母。对于 must-recover，错误终止才是 FP；未误停可记 TN，**TN 并不等于任务最终修复成功**。

此次直接对 36+36 条 Result 与逐 Trial Trace 执行独立分类核算，得到：

| 指标 | 统一 Baseline | 统一 Candidate | 可作何解释 |
|---|---:|---:|---|
| Run ID | `20260910T154937Z` | `20260910T173833Z` | 都是原始完整 DEV×3 |
| 全量 Trial | 36/36 | 36/36 | 两组没有缺失 Trace |
| TP / FP / TN / FN | 11 / 0 / 18 / 7 | 13 / 0 / 18 / 5 | 按修订后的原始终止事实复算 |
| Stop Recall | 11/18 = 61.11% | 13/18 = 72.22% | +2/18，约 +11.11 个百分点 |
| False Stop Rate | 0/18 | 0/18 | 这一批数据没有观察到误停，不证明概率永远为 0 |
| Governance Accuracy | 29/36 = 80.56% | 31/36 = 86.11% | 包含 infra-error Trial 的保守分母 |
| 必须恢复任务实际完成 | 14/18 | 15/18 | 不可直接用 TN=18 替代 |
| 独立 Verifier 通过 | 22/36 | 24/36 | 包含两类任务的验证结果 |

这组运行具有相同的任务、模型和 Config SHA，为阶段性的对照提供了较好的条件控制；但 Candidate dirty、Trial 随机性、Infra Error 分布不同，以及经过事后修订的评分解释，使其不满足“精确已提交版本的强因果 A/B”。尤其 7→3 的 Provider 错误数量差别会影响轮次、耗时和 Token 均值，不能用它们直接宣称 Runtime 改善了相应百分比。评分修订没有重新运行模型，因此也不代表在当前 `main` 重新达到上述分数。

### 2.2 真实 Trace 解释了什么，而不是只看比例

**task019 永久服务不可用**：Baseline 的 `trace_task_019_permanent_service_outage_r01.json` 共 11 轮、14 次工具调用，曾得到 HTTP 503/服务不健康线索，却最终以 `SUCCESS` 结束，独立 Verifier `FAILED`；这是“进程命令表面执行成功/模型继续调查，却没有正确终止”的例子。Candidate 同任务 r01 也有 11 轮、14 次调用，但早期 `service_probe.py` 返回非零及 `NETWORK_UNREACHABLE`，后续经历再次失败、`REPLAN`、写报告，最终由 Completion Gate 以 `BLOCKED_ENVIRONMENT` / `UNRESOLVED_BLOCKER_COMPLETION` 阻止未经证实的完成声明。它给出的技术因果是：保留失败观察与未解决阻断，比依赖模型最后一句总结更可靠。**单例并不能独立证明所有 HTTP 失败都能被识别。**

**task023 可恢复权限缓存**：Candidate r01 共 7 轮、7 次工具调用。`build_export.py` 初次执行产生 `PERMISSION_DENIED`，随后 Agent 修改 `cache_config.ini` 中输出位置，再次运行同一导出工具返回 Exit Code 0，最终读取 `artifacts/orders.json`，`final_status=SUCCESS`、Verifier 成功。这条完整轨迹把“允许重复调用一个失败命令”与“无意义地无限重试”区分开来：源配置发生真实变化，而且同一目标被正向验证，故不应仅根据调用重复性实施硬停止。

**task033 状态振荡**：Candidate r01 的 Shell 观察依次包含 `OBSERVED:A`、`OBSERVED:B`、`OBSERVED:A / OBSERVED:B`，工具事件出现 `semantic_state=a`、`b`、`a|b`，并触发 `REPLAN`；该 Trial 最终 `BLOCKED_ENVIRONMENT`。可确认的是反复变化的状态没有被简单当作正向进展，且未以模型的成功文本直接完成；不能把一个状态循环例子推广为任意异步服务收敛检测已经解决。

### 2.3 Candidate Smoke 与正式 Candidate 不能混在一起

压缩包还有 `anti_loop_unified_candidate_smoke/` 下四个 Run ID：`20260910T163621Z`（12 个无 Trace 的 Infra Error）、`20260910T163724Z`（12 个完成 Trial）、`20260910T164709Z`（12 个完成 Trial）、`20260910T172903Z`（12 个完成 Trial）。它们**不是上述 `20260910T173833Z` 的正式 36 Trial Candidate**，有不同的中途修复状态和结果；前一组没有 Trace 的记录只能算评测运行失败，不允许静默排除或混入 Candidate 的成功数。压缩包还包含 `20260910T165755Z` 的另一份 36 Trial 候选，不能用这份早期结果覆盖最终审计账本。

## 3. V2 Baseline 0：不是 Unified 对照中的下一条同口径数据

归档内 `anti_loop_v2_baseline_0_20260911/` 包含 `run_manifest_20260911T094634Z.json`、`run_results_20260911T094634Z.json`、36 条 Trace 和 `anti_loop_benchmark_v2_dev_baseline_report.md`。此版本 `agent.commit=491a150ea910349d912dc8f83add8267fc8a2eba`、工作树干净，但 `task_suite_sha256=e867166a6495a2377e9cc25a2d202ff8c521489634da8ac3ec40cf38a45bf02c`，评分及任务合同版本均为 2，已与之前 Unified `6ded4f86...` 发生变化，**不得用它与 Unified 直接计算 delta**。

原始数据直接复核了报告的计数：36 次全部归档，Raw Governance `TP=11, FP=1, TN=17, FN=7`，Verifier `10/36`，Infra Error `9/36`，其中 Provider timeout 8 次、工具/环境解析异常 1 次。报告还标注 task022 三个 Validity Incident：当时 Agent 执行了 health 503→start 200→health READY 200→orders/42 PAID 200 的实际步骤，但 Verifier 自身错误读取了 Agent 专用凭据而抛 `KeyError`，**不可把这三次判为 Agent 恢复失败**。

在明确剔除 9 项 Infra Error 和 3 项 Bench Validity Incident 后，报告所定义的有意义样本是 24 项：Grounded Success `10/24`，其中正确 Grounded STOP 3 项（task020 三次）、恢复成功 7 项（task023 三次、task031 一次、task032 三次）。这是 V2 的“解释性样本”口径，不是重新计算原始全量 Raw Governance 的分母。9 项 Infra 和 3 项 Validity Incident 均保留在 36 Trial Ledger，不允许从原始记录删除。HOLDOUT 动态模型试验为 0。

从完整 Trial 可以看到评测发展的因果：旧 STOP/CONTINUE 分类在缺少业务证据时就可能得分；V2 不仅要求有正确终止形态，还要求对 STOP 的判定引用独立验证的目标 Observation。这样的信任边界改善会**降低数字表面上的可比性，却提高指标的业务含义**。这一变化不能声称已解决所有 Grounded Evidence 问题。

## 5. 需要主动防止的指标误读

1. Unified 的 11/18→13/18 是**按修订后的评分器从旧原始结果重新计分**，不是当年 `run_results` 旧缓存字段自己相加的结果；要记录算法口径与源文件版本。
2. Unified Candidate Worktree dirty，无法仅凭同一 `agent.commit` 绑定候选版本；建议将“较好的阶段性结果”与“完全可复现的干净 Git SHA A/B”区别陈述。
3. V2 Benchmark 合同与任务 hash 已变，且含明确的 task022 Verifier 有效性事故；不与旧 Unified 报告直接并列为性能提升序列。
4. Harness 把某个 Trial 记录为 reward 0，并不说明模型“完全没有思考”；Trace 显示大量有效调查，但工程目标仍未完成。评价能力应同时看真实源码 mutation、最终 Verifier 和资源预算。
5. Todo 超时 Trial 缺少最终 Trace/Provider usage，不能填入使用量推算，也不能把 0.0 reward 当成一个真实完成后失败的样本。

## 6. 对既有知识底稿的影响

本文件将 [01](01_Agent循环与失败治理.md) 与 [06](06_评测体系与证据可信性.md) 中引用的 Unified 对照由“历史报告描述”提升为“**已读取原始 Manifest、36+36 Results 和每次 Trace，按审计规则重新核算**”。[03](03_上下文工程与Prompt演进.md) 中的 MIPS Failure 现在也有原始 Token/调用序列/Verifier 支持，结论依然是“这些 Trial 失败，没有足够证据证明 Prompt 或结构化记忆带来实际成功率改善”。[07](07_证据索引与遗留问题.md) 后续应仅把尚未提供的其它试验单独列为缺口，不再泛称整个 Unified A/B 和这三组 Harbor MIPS 原始记录均缺失。

本次没有额外执行测试、没有启动 Provider、没有修改代码/测评输入，也没有上传含凭据的原始 ZIP。未来如需复算，可按以上归档 SHA256 校验对应 ZIP，使用仓库 `scripts/audit_anti_loop_accounting.py` 配合适配版本的 `src/core/evaluation/anti_loop.py` 加载 Result + Trace；必须同时检查评分规则是否与当时报告一致。
