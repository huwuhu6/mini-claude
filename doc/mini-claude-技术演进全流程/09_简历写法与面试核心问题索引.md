# mini-claude 简历写法与面试核心问题索引

本篇是整个项目的“先学什么、简历怎么写、面试怎么答”入口。详细技术演进仍见 00—08；各主线的简历写法和问答已追加在 01—06 篇末尾。这里先给一份可以直接复习的简历草稿、优先级索引和面经来源。

## 一、简历项目描述建议

建议简历只保留 3—4 个彼此能形成技术故事的点，不要把每个模块都写成一条。下面的描述可按目标岗位取舍。

**项目概述**：基于 Python 开发的 Coding Agent，支持模型通过工具读取和修改代码、执行命令，并根据工具结果持续推进任务；围绕长任务执行中的重复操作、上下文膨胀、意外中断和高风险操作审批进行工程化改造。

**推荐版本 A：偏 AI 应用 / Agent 工程**

- **Agent 执行治理**：针对工具调用重复、环境故障下无效重试及未经验证的完成声明，完善执行记录和失败治理流程，结合真实工具结果判断是否继续、停止或重新规划。
- **上下文成本控制**：将长工具输出保存为文件并支持按需回读，结合历史消息压缩与工具调用配对检查；在长日志中间信息定位任务的 5 次对照中，平均 Token 从 253,998 降至 79,288，下降 68.8%，两版任务均通过验证。
- **断点恢复与安全审批**：基于运行状态和 SQLite 执行日志记录工具调用进度，恢复时区分已完成、尚未开始和结果不确定的操作；为敏感工具接入人工审批，保留原始调用并在批准后继续执行。
- **评测体系**：构建包含任务配置、独立验证器、模型运行记录与逐轮工具轨迹的评测流程，识别验证器凭据错误等测量问题，避免把 Agent 执行失败与评测设施故障混为一谈。

**推荐版本 B：偏 Python 后端 / 工程基础设施**

- 统一工具定义、参数校验与执行分发，结合功能开关、工作区授权和执行时检查控制工具调用。
- 使用 SQLite 保存运行状态、工具操作日志和审批记录，支持进程重启后的状态恢复，并对结果不确定的副作用操作采取保守策略。
- 完善长日志外置、上下文压缩和评测轨迹记录，降低特定长日志任务的模型 Token 消耗并提高问题复现能力。

### 简历使用说明

1. 若简历空间有限，优先保留上下文成本控制、断点恢复/人工审批、执行治理三条；工具注册可以融入第一条或作为面试细节。
2. 68.8% 只适用于 `task_014` 的特定长日志诊断对照，样本是每版 5 次，不应写成全项目 Token 普遍下降 68.8%。
3. Unified Anti-Loop 阶段性结果的 Candidate 工作树当时未提交，因此不建议在简历中写“某个正式版本将 Stop Recall 提升 11.11 个百分点”。可以在面试中作为实验迭代案例说明。
4. 没有在当前远程主线中核实 MCP Client/Server 实际接入，简历不要写“实现 MCP 全链路”。Skill 文件发现和按需加载可以按实际代码讲解。
5. 最终简历措辞还需与你实际准备投递的简历版式、项目篇幅和岗位 JD 对齐；本篇给的是内容素材，不代表所有点都应同时放入一份简历。

### 如何使用 P0/P1/P2

- **【★★★ 必会】**：简历写了就必须能讲清楚；核心执行路径和关键异常场景至少能应对两轮追问。
- **【★★ 重点】**：理解实现、主要取舍与适用边界，能结合项目举例。
- **【★ 拓展】**：知道概念与边界即可；没有实际实现的方案明确说是替代思路，不包装成项目成果。

真实面经题在专题里标注为“真实面经相关”；围绕具体类、状态和失败时序的问题标注为“项目深挖”。如果一道题虽然在面经出现过，但与本项目实现关联较弱，不应仅因其出现过就占据最高优先级。

## 四、最省时间的复习顺序

第一轮只看本篇 P0 索引和每篇的简历写法；第二轮合上答案，自己口头回答 P0；第三轮再补 P1 中的异常处理和方案取舍；最后再看拓展题。每道 P0 至少准备一个真实代码路径或评测例子，避免回答停留在概念层面。

面试时如果遇到项目没实现过的功能，可以说明“当前项目做到哪一步”，再给出自己的理解和可能方案。重点是分清实践事实与方案推演，而不是为了答题完整把没有做过的功能说成已经落地。
