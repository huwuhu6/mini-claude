# 工具、执行环境与扩展边界：从分散 handler 到受约束的 Tool Registry

> 基线 `5f41f1d09806ed8a4c387bd80b47a07adaa45609`。源码：`src/core/tools/registry.py`、`definitions.py`、`base_tools.py`、`src/agent/mini_claude_agent.py`、`src/core/runtime_context/`、`src/skills/loader.py`。历史：`docs/evolution/tool_registry.md`、`tool_deduplication.md`、`polyglot_environment_guard.md`、`cli_command_boundary.md`。重点区分“Provider 看得见”“Registry 有 handler”“运行时允许执行”三层不同事实。

## 1. 为什么工具系统不是简单的 Python 函数表

让模型修改仓库至少涉及三个环节：告诉模型它有哪些可调用工具、收到模型请求后确定执行哪个函数、在执行前确认参数/工作区/权限都有效。初期每增加一个工具，如果 Agent 内有一份 JSON Schema、SubAgent 有另一份、Runtime 又手工按工具名分支，三处很容易漂移：模型能调用已关闭的功能，或同名工具参数在不同执行者上表现不一致。后续必须追问：**工具描述和真正 handler 是否来自同一个可审计契约**。

2026-10-01 的 `9dad692`、`330e11d` 代表重构：`ToolSpec` 同时保存 `name`、`description`、`input_schema` 和 `handler`，`ToolRegistry.register()` 拒绝重复注册。`definitions()` 从已注册项生成 Provider 所见的函数描述，`execute()` 再从同一项找到 handler。`ToolArgumentBindingError` 在 handler 之前用 Python `inspect.signature.bind(**args)` 检查实际方法参数；它与 handler 内部自己抛出的 `TypeError` 属于不同错误来源。`execution_contract()` 还尝试获取 handler 源码并计算哈希，供受控恢复时的兼容性检查。

需要格外强调：**Registry 本身不是权限沙箱**。它负责注册、Schema 提供、简单参数绑定与分派；`WorkspaceAuthority`、`CommandPolicy`、Feature 能力门禁和 HITL 权限决策位于外层的 Agent/Runtime 执行路径。直接调用 `registry.execute()` 不会天然经过持久化审批。因此本项目权限只对已经接入指定执行入口的主 Agent 运行路径作承诺。

## 2. Provider 看见工具之后，程序还要再检查一次

工具注册与功能开关有两个时间点。构造本轮模型请求时，`_get_llm_tools()` 决定对模型暴露哪些工具；但模型响应可能稍后才到达，期间 Feature 已关闭或 handler 集合发生变化。仅凭“发请求时模型能看见”作为执行许可，存在时序漏洞。`3f61cee（历史提交短 SHA）` 因此在 `_execute_tool()` 真正分派前检查 `tool_registry.has_handler(name)` 和 `feature_manager.is_tool_enabled(name)`。禁用返回可辨认的 `FEATURE_DISABLED` ToolDispatchResult，不能悄悄调用真实 handler；未知工具返回 `UNKNOWN_TOOL`。这次改造的重点是 **dispatch-time authorization**（执行时能力校验），而非修改模型 Schema。

按当前代码走一个说明性场景：模型在请求中看到 `bash`，但等待返回期间相关功能被禁用；收到 `bash` Call 后，`_execute_tool()` 查询当前 Feature 状态，返回不执行原因，Tool Result 仍对应原调用 ID。若显式启用 HITL，则还会先进入 `_hitl_gate()`，硬拒绝或待审批优先于真正 handler；已有待批准操作恢复时还会重新校验原调用身份和策略绑定，不能把过期批准用作新的执行许可。

## 3. Shell 与文件工具为何必须共同依赖 Workspace

文件读取、写入、编辑及搜索都通过 `BaseTools` 实现，路径解析及可访问范围的最终约束由 `WorkspaceAuthority` 协调。单纯检查文件字符串是否包含 `..` 不够：相对路径取决于 `cwd`，符号链接可能改变真实目标，当前工作目录也可能在两次 Shell 之间发生变化。`src/core/runtime_context/path_resolver.py`、`workspace_authority.py`、`workspace.py` 和 `shell_session.py` 分别处理路径与当前执行上下文；`BaseTools.safe_path()` 体现工具侧对这些约束的使用。

Shell 命令的另一个问题是状态不能由“最近一条显示文本”来定义。历史上 Windows `start` 启动 Java 服务时，服务已启动却使 Agent 对应的同步工具调用长时间不返回；后续通过独立后台任务和 `health_check` 区分“启动包装进程状态”和“真正服务健康”。这一块当前属本机后台管理能力，**不在 SQLite Checkpoint 对前台原调用的恢复保证内**，也不能声称进程退出后被自动接管。`123586a` 修复的 `ShellSession` cwd 与环境继承语义，则要理解为对命令所在目录的确定性维护：一条命令在另一个目录运行，不应因状态回传格式造成后续工具都使用错误 cwd。

历史文件 `docs/evolution/tool_deduplication.md` 还提到长输出首先写 `.agent/logs`，模型只收到部分头尾预览和可访问的日志路径。这属于工具结果展示策略，不等于丢弃原始诊断。后来默认阈值调整到约 200 行或 4,000 字符，并记录输出可见性；详见 [03_上下文工程与Prompt演进](03_上下文工程与Prompt演进.md)。

## 4. Tool Result 为什么不能只返回一段字符串

假设运行 `pytest`，进程返回代码 1、stderr 包含若干测试失败；模型需要可读文本决定怎么修，Runtime 需要原始退出码与失败证据决定是否重试、终止。若工具格式化后只剩“最后执行成功”，就无法知道哪个命令失败；若为了节省 Token 只返回首尾日志，又必须给模型安全读取完整日志的路径。于是 `ToolResult` 包含 `content` 与结构化成功/输出状态，`ObservationNormalizer` 再依据工具上下文判断可归因故障。工具输出格式化本身不能把普通字符串中的“HTTP 503”一律当作当前真实网络失败。

输出正确性与消息协议正确性还是两回事。Provider 一次返回三个工具调用，第二项因权限被拒、第三项因取消未执行时，Runtime 需要保留三个不同 Provider Call ID 的结果。`_close_tool_call_batch()` 按已解决 ID 补 `NOT_EXECUTED`/`UNKNOWN`，`ToolBatchState` 记录当前游标。工具消息在状态持久化前后的故障怎样处理，则交给下一层 Checkpoint；这条边界非常重要，Registry 并不拥有“恰好一次”的副作用保证。

## 5. Tool、Skill、MCP 和 Plugin 到底有什么关系

**Tool（工具）**：由 Provider Tool Schema 告诉模型如何调用，Runtime 注册 handler 并决定可否执行。当前本地文件与 Shell 工具属于这一层，`ToolSpec` 是主要契约。

**Skill（技能）**：是携带说明和可选辅助资源的知识包，首先改变的是模型能获得哪些领域操作指导，不自动代表有新执行权限。当前 `SkillLoader` 扫描平面 `*.md`/`*.yaml` 与子目录的 `SKILL.md`，读取简化 frontmatter 的 `name`、`description`、`triggers`、`version` 等，允许通过 `get_skill_content()` 返回正文，`find_matching()` 只按关键词匹配。`src/agent/mini_claude_agent.py` 的 `_handle_load_skill_dispatch()`/`_load_skill_internal()` 展示了加载入口。发现 PDF 技能目录中有脚本，并**不等于脚本自动获得执行权限**；若模型后来用 Shell 运行脚本，仍经过 Shell/工作区/Feature/权限约束。当前 Loader 采用发现时文件解析与缓存，不要误称它把所有 Skill 的完整正文“绝对按需才读取”；按需主要指正文何时进入模型上下文。

**MCP（Model Context Protocol，模型上下文协议）**：从职责上可让外部 Server 提供 Tools/Resources/Prompts，并由 Client 发现和调用。审计的 `main` 文件树未见 MCP Client、Server、Adapter 实现，`ToolRegistry` 也未发现已证实的 MCP Tool 接入路径，因此只能列为知识背景/未落地扩展。不要虚构多 Server 命名冲突处理、Resources 动态注入或第三方权限隔离已经实现。

**Plugin（插件）**：行业中语义不统一。仓库当前没有已证实的 Plugin Runtime 安装、签名、权限授权和隔离机制；仅凭技能和工具可以组合使用，不应将其描述为成熟插件平台。测试中出现名字带 `plugin` 的任务文件，也不说明宿主具备插件管理能力。

## 6. 多 Agent 的“存在”与“启用”不可混淆

`src/core/subagent.py`、`teammate_manager.py`、`messaging/bus.py`、`background.py` 等扩展基础设施确实存在，但 2026-10-01 `9965ffc（历史提交短 SHA）` 标记对尚未完成闭环的多 Agent 基础设施进行冻结。不能把“文件存在、历史文档描述了四种 Agent 类型”当作“当前 CLI 默认提供成熟协同多 Agent”。尤需注意，Checkpoint 模式会直接拒绝后台和 SubAgent 执行：恢复的承诺仅覆盖主 Agent 前台批次。这样的收敛是合理的范围控制，而不是暂时遗漏要靠宣传补齐的特性。

早期 `TodoWrite` 又属于另一种状态：曾移出模型可见 Schema，`eb1b021d375929c405d30a72be418b29fc00059f` 后在主 Agent 恢复为运行内轻量任务进度状态；其状态和运行期临时上下文关联，但不保证模型一定主动调用。`docs/HANDOFF.md` 的一次 Harbor 试跑达到 1800 秒时限，模型没有调用 TodoWrite，证明“工具开放”与“模型实际采用”不同。

## 7. 执行权限在哪里决定，尚未解决什么

当 HITL 打开时，`DefaultPermissionPolicy` 在 Tool Operation 层进行 `DENY` / `ALLOW` / `ASK` 决策。未知工具、已禁用功能、参数不匹配、越界路径、被 `CommandPolicy` 硬拒绝的 Shell 命令首先 DENY；明确核验的内置只读 handler 可以 ALLOW；其余操作保守 ASK。绑定操作时收集原 Tool Call、run、当前 ordinal、cwd、Workspace 和源码/Runtime/策略摘要。审批后仍需重查这些事实，不能让批准绕过真正的硬性规则；详情见 [05_HITL审批与执行安全](05_HITL审批与执行安全.md)。

但是代码级检查无法保证第三方命令被 OS 层完全隔离，也没有阻止具授权文件读取权限的进程通过其他渠道访问所有信息；Shell 沙箱、进程级身份认证、网络隔离、MCP Server 非可信工具隔离，均不是当前已证实的能力。一个注册过的工具如果由用户代码直接绕开 `_execute_tool()` 调用，也不会受该外层审批保证保护。由此得出工具系统的真实边界：**Registry 保证“可找到何种能力”，Feature/Authority/Permission 保证“这次是否允许”，Checkpoint 才尝试保证“恢复时不会不确定地重复调用”**。三者不能用一个“工具安全”概念概括。

## 8. 验证、遗留限制与迁移含义

源码对应的回归包括 `tests/unit/test_tool_registry.py`、`test_tool_observation_reliability.py`、`test_tool_batch_message_closure.py`、`test_workspace_authority.py`、`test_permissions.py`、`test_shell_session_state.py`、`test_dormant_multi_agent.py`。历史 `docs/evolution/tool_registry.md` 报告 `8c7af3e` 相关 Windows 定向测试 117 passed/10 skipped，Linux Docker 相关测试 160 passed/1 skipped/1 deselected；`3f61cee` 相关 136 passed/10 skipped。这些是**历史测试报告**，本轮没有重新运行测试。不同平台 skip 必须原样保留，不能统称“跨平台全通过”。

下一层工程价值在于：即使 Tool Registry、Handler 和权限都执行正确，进程仍可能在真正产生副作用后崩溃，此时再次调用原 Handler 可能造成重复写入。仅凭 Trace 或 Session 也无法可靠知道上一次的工具操作有没有真正执行。所以后续 RunState 与 Checkpoint 的根因是**副作用事实缺少可靠提交边界**，详见 [04_RunState快照与Checkpoint恢复](04_RunState快照与Checkpoint恢复.md)。


## 面试准备：简历提炼

**推荐写入简历（P1，可与 Agent Loop 合并）**：把工具描述、参数定义与实际执行函数统一注册，并在真正执行时检查功能开关与工作目录权限。相比强调“支持很多工具”，这更能体现从 Demo 到工程化执行的设计。

**简历写法**：重构工具注册与调用链路，统一工具参数定义、执行分发和错误处理；结合功能开关及工作区权限校验，保证模型请求的工具在执行前经过实际能力检查。

MCP 在当前主线尚无已核实的客户端接入，不推荐写成项目实现亮点；但其原理可能出现在面试中，需要掌握。

## 面试 Q&A

**【★★★ 必会｜真实面经相关】Q1：模型是怎么调用工具的？是自己执行 Shell 吗？**

答：不是。我们会提前给模型一份工具清单，告诉它有哪些工具、每个工具需要什么参数。模型返回的是“我要调用哪个工具、参数是什么”，程序拿到后才会检查参数和权限，再找到对应函数去执行。执行完成还要把结果关联回原来那次调用，让模型知道刚才发生了什么。模型能提出调用请求，不代表它拥有无限执行权限。来源：[牛客·字节 Agent 岗的工具调用流程](https://www.nowcoder.com/discuss/922659486983036928)。

**【★★★ 必会｜项目深挖】Q2：为什么要统一 Tool Registry（工具注册表），而不是每个工具都写一个 if 分支？**

答：一开始工具不多，用分支处理确实简单。但以后工具变多，模型看到的参数说明、程序实际分发的位置、功能开关的判断很容易分散。重构以后，工具描述和执行函数统一注册，模型看到的清单与程序真正能调用的函数来自同一处。收到调用时先检查工具存在、参数匹配，再执行对应函数。这样新增或禁用工具时不需要维护好几份容易不一致的定义。

**【★★★ 必会｜真实面经相关】Q3：Tool、MCP 和 Skill 分别解决什么问题？**

答：Tool 是具体能执行的动作，比如读文件、运行测试。MCP 是让外部工具服务用统一方式向 Agent 提供能力的协议，可以理解为外部工具的标准连接方式。Skill 则更像一份按需使用的操作指南，告诉模型做某类任务有哪些步骤或注意事项，它本身不等于拥有执行权限。我这个项目已经有本地工具注册和 Skill 文件加载，但没有把 MCP 客户端接入说成已完成能力。来源：[牛客·字节 2026-10-12 的 MCP、Skill、Plugin 对比题](https://www.nowcoder.com/discuss/940390952902914048)。

**【★★ 重点｜真实面经相关】Q4：如果模型一次要求调用三个工具，怎么处理顺序和对应的结果？**

答：先保留模型返回的三条原始调用及其唯一标识，再按实际执行策略逐个处理。每处理完一个，就把结果挂在原来的调用标识下面，避免模型把 A 的结果误当成 B。如果第二个工具被拒绝或程序要暂停，不能直接跳过并留下不完整的消息；应该保存剩余调用，或者给未执行的调用补上明确的未执行结果。这也直接关系到后面的断点恢复。来源：[牛客·字节 Agent 岗，多个工具连续执行的顺序问题](https://www.nowcoder.com/discuss/922659050167226368)。

**【★★ 重点｜项目深挖】Q5：为什么模型能看到一个工具，执行时还要再检查一遍？**

答：因为模型发出请求与程序真正执行之间有时间差。这个过程中工具可能已经被禁用，工作区也可能改变。如果只依赖请求时的工具清单，就会出现已经关闭的能力仍被执行。最终执行前再查一遍是否存在、是否启用、参数与路径是否合法，才能以实际执行时的状态为准。

**【★ 拓展｜项目深挖】Q6：Skill 中包含脚本，加载 Skill 是否就意味着可以运行脚本？**

答：不是。加载 Skill 只是让模型读到对应的说明和资源位置。模型之后真的要运行脚本，仍需要正常发起 Shell 工具调用，并接受同样的权限和路径检查。
