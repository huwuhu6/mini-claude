# Evaluation、Benchmark、Harbor 与证据可信性：从记录分数到校验测试契约

> 代码基线 `5f41f1d09806ed8a4c387bd80b47a07adaa45609`。源码：`eval_runner.py`、`compare_reports.py`、`benchmark/harbor/agent.py`、`src/agent/headless.py`、`src/core/evaluation/`、`src/core/tracing/`、`scripts/rescore_anti_loop.py`、`scripts/audit_anti_loop_accounting.py`。参考历史：`docs/EVALUATION.md`、`docs/evolution/evaluation_evolution.md`、`anti_loop_benchmark_audit.md`、`anti_loop_task022_validity_incident_closure_report.md` 和 tracked `eval_reports/`。重要：未执行新的付费模型试验，本文复核的是**远程已存档的报告、实现和历史测试记录**。

## 1. 为什么真实模型 Trace 也可能给出错误结论

Coding Agent 的结果至少有三个判断层级：“工具是否执行成功”“最终代码/业务结果是否成功”“Runtime 遇到失败时是否正确停止或继续”。如果把这些统一压缩为一个“最终是否回复成功”，模型没有修改目标文件也可能因为输出了漂亮总结得到正向标记。即使单测/Verifier 返回通过，也可能只说明验证器接受了一份作弊式哨兵文件，不能证明目标服务真的启动、订单状态真的变更或测试真的完成。

mini-claude 早期 `eval_runner` 已能执行沙箱任务，但历史演进实际暴露两类独立问题：一是**评测数据身份不稳定**（不同 Fixture、不同验证器和 Agent 版本却直接比较），二是**Oracle 测量有缺陷**（Verifier 接受伪造结果或自己读取错误凭据）。因此 Evaluation 这条主线不只是最后附录，而是持续修改架构验证方向的工程组成部分。

## 2. 从简单任务运行到可追溯的 Trial

当前 `sandbox/tasks/<task_name>/` 通常包含 `config.json`、`baseline/` 和可选 `verify.py`。`eval_runner.py` 在影子工作区执行任务，不应污染被版本控制的 baseline；`--validate-only` 在不导入 Agent/请求 Provider 的条件下审查契约。对合法 Case 至少应确认目录名称与 Case ID 一致，Prompt 非空，baseline 存在，配置显式声明验证脚本并禁止越权路径。

为什么 `--validate-only` 必须独立？旧流程在仅想检查任务文件时也可能初始化 Agent、依赖模型 API Key 和 Token 编码资源；任何外部环境问题都可能使评测契约检查无法运行。拆开后既能在 CI 中快速检查，也可在运行付费模型之前发现潜在误评分。历史 `docs/evolution/evaluation_evolution.md` 记录过 `task_007` 的 `verify.py` 因没有声明而被跳过，这类错误会把本来该失败的目标报告成“没有验证”，污染成功率。

此后系统加入 `run_manifest_<run_id>.json`：关联 Agent Git Commit、dirty 状态、Python/平台、任务集摘要、每项 config/baseline/Verifier 哈希以及 Provider 配置；`run_results_<run_id>.json` 逐 Trial 保存结果与异常；`trace_<case>.json` 则提供轮次、工具、时延、模型请求和治理事件的轨迹。`compare_reports.py` 需要同时读取这些来源，不能只对文件夹名做平均。当前还区分完整 Trial Ledger（已尝试任务包括 CRASH/无 Trace/基础设施错误），避免失败试验从分母中无声消失。

## 3. 什么才算可比较的 A/B

基线和候选最少要确定**任务一致、验证契约一致、环境条件一致或已明确记录差异、模型/Provider/温度等条件可核实、原始运行次数完整、两个 Agent 实现版本可定位**。单次 Trial 受模型随机性影响大；小样本均值必须记录范围、通过率及失败分类。不同 `task_suite_sha256` 的对比并非完全没有参考价值，但不能将变化直接归因于 Runtime 代码。

一个明确反例是 `eval_reports/anti_loop_refactor/comparison.md`：历史候选聚合看起来成功率和 Token、耗时都有大幅改善，但报告表头已经警告 Baseline hash `d561dd34` 与候选 hash `a2dcc5ab` 不同，任务集合并非严格同一版本。该对比只能用于追踪当时测试体系在变化，不能成为简历或正式工程基准中的统一“提升率”。模型/环境/任务都改变时，错误归因的风险尤其高。

### 3.1 成功率和治理指标应独立

Anti-Loop 套件把任务分为 `must_stop`（环境阻断且应停止）与 `must_recover`（一次失败后还有合法恢复路径）。治理分类定义为：正确停止记 TP，应停却未停记 FN，误停可恢复任务记 FP，没有过早停止可恢复任务记 TN。常用指标：

`Stop Recall = TP / (TP + FN)`；`False Stop Rate = FP / (FP + TN)`；`Governance Accuracy = (TP + TN) / 总 Trial`。

但是 `must_recover` 记 TN **并不说明任务完成成功**：Runtime 继续执行却没有修好代码，治理上不是“误停”，业务 Outcome 仍是失败。反过来不可恢复任务正确停机，不能因为没提交代码被统一判为“Agent 能力失败”。因此还应报告 `Solvable Success Rate`、Verifier Pass、Infra Error、没有 Trace 的 Trial 和真实输出行为。`Stop Precision` 对应 `TP/(TP+FP)`，分母含义和传统二分类场景容易混淆，必须按本项目的约定解释。

## 4. 一条真实的 Benchmark 演进失败链

初期 Anti-Loop Case 过分依赖 `solution.txt=RECOVERED` 之类哨兵，意味着模型不启动服务、不解决权限路径，只要创建一个预期文件也可能拿到“恢复成功”。审计的具体例子包括可恢复网络、Permission denied、模块缺失与状态轮询任务。`docs/evolution/anti_loop_benchmark_audit.md` 明确把多数 recover Case 评为 LOW，禁止据此对外宣称强业务恢复能力。

后续 Fixture/Verifier 开始建立实际不变量：例如 `task_022` 要有受控服务 health READY 且订单端点业务值符合约定；`task_023` 验证 JSON artifact 的结构和 SHA256；`task_024` 运行实际本地组件并检查数值；`task_025/026` 由 Verifier 独立运行 pytest；`task_027` 将状态推进放入 evaluator-side 的受控状态机并校验导出制品。这里的关键思想是**让业务结果由独立验证者重算，而不是相信 Agent 写的“成功”字符串**。Task hash、原始用例和变更时间都必须保留，避免用后来的强验证器误解早期生成的分数。

## 5. task022：真正成功却被验证器判失败的测量事故

`docs/evolution/anti_loop_task022_validity_incident_closure_report.md` 保留了一次典型事故。Baseline `20260911T094634Z` 的三个 `task022` Trial 中，原始 Trace 显示 Agent 先从 `/health` 取得 503，再访问 `/start` 返回 200，随后 health 变 READY，`/orders/42` 返回符合业务合同的数据。然而 Verifier 执行时触发 `KeyError: EVAL_FIXTURE_TOKEN`，导致原始结果误列为 `FAILED_RECOVERY` / `RECOVERY_UNGROUNDED`。

根因不在 Agent 恢复策略：原 Runner 只向 Agent 环境注入 Agent 业务凭据，而给隐藏验证器的是独立的 Verifier Token/Trial ID/URL；`task022` Verifier 却读取 Agent 专属环境变量，违背了已有的信任边界。正确修复不是“为了让测试通过，把 Agent Token 也给 Verifier”，而是让验证器使用独立的可信审计接口重新验证业务事实。原三条 Trial 应永久标记 `BENCHMARK_VALIDITY_INCIDENT`，保存原始结果与 Trace，再单独运行 replacement，并在 reconstruction manifest 中说明替换历史，不得覆盖原 JSON。

这解释了为什么“Verifier 失败”不能立即等同于“Agent 失败”，也解释了为什么测试基础设施的凭据隔离、数据来源和权限界面本身也是需要审计的架构。后续 Hardening v2 把 Agent-visible API 和仅 Verifier 可见的 `/audit` / `/state` 分离，通过不同 Token 与 Trial ID 绑定保护原始证据；但存在历史报告标为 BLOCK 的动态 Smoke，不能把静态 mutation 测试“通过”写成真实动态能力证明。

## 6. Anti-Loop 的真实历史数据怎样逐层解释

第一组 `docs/evolution/anti_loop_benchmark.md` 记录早期冻结 DEV×3 36 Trial：TP=3、TN=14、FP=4、FN=15，Accuracy=17/36=47.22%，False Stop=4/18=22.22%，Appropriate Stop=3/18=16.67%。这些数字用于解释为什么要改造分散失败计数、观察证据、状态振荡与阻断完成判断，不代表当前代码的最新能力。

第二组 `docs/evolution/anti_loop_benchmark_audit.md` 记录后来统一 Attempt Event 重构阶段的 DEV×3 Baseline/Candidate：Stop Recall 11/18→13/18，False Stop 0/18→0/18，Verifier Pass 22/36→24/36。此时 Provider 可用性和相同任务/manifest 条件仍须对照报告核验；它证明在指定实验与评分口径下有观察差异，而不是每次 Runtime 变更都有这项收益。

第三组“Resolution Boundary”后的 Candidate DEV×1：12 Trial，TP/FP/TN/FN=5/0/6/1，Verifier Pass 9/12、Infra Error 3/12。该报告明确表示基础设施故障过多、没有完成 DEV×3，不应把 91.67% Governance Accuracy 当作稳定上线指标。某次 Candidate DEV×3 甚至全部受 Provider HTTP 402 余额不足影响，导致零可比较试验。这与“把不成功的 Trial 从分母里删掉”相反：必须保留并正确分类。

## 7. Tool 长输出的两个可解释对照

这部分既属于上下文优化，也验证 Evaluation 如何改进可信性。`eval_reports/log_to_file_refactor_v3/compare.md` 的 `task_013` 清理后对照：`c656000f` 与 `f0b29086`、同任务 hash `d428474a`、Windows Python3.12.1，每版五次，Verifier 5/5 对 5/5，平均 Token `54,693→39,147`（-28.4%），平均轮次 `7.4→8.2`（增加），平均耗时 `10.842→11.872s`（增加）。早期同名 Task 的 `143,457→47,960`（-66.6%）已被识别受 Fixture 提示泄露和极端样本影响，不能优先用旧版。

`eval_reports/log_to_file_refactor/task014_compare.md` 的 `task_014` 是另一种任务：唯一诊断行位于长日志中间，`5111599f` 与 `2dd60c22`、hash `f440451f`，每版五次且均成功，平均 Token `253,998→79,288`（-68.8%），平均轮次 `14.8→13.8`，耗时 `22.588→21.590s`。它说明特定中间日志任务的输出外置有帮助，绝不能给“所有上下文管理”和“所有 Agent 执行”统一冠以 68.8%。完整工程机制见 [03](03_上下文工程与Prompt演进.md)。

## 8. Terminal-Bench/Harbor 主要暴露了什么失败

当前 `benchmark/harbor/agent.py`、`src/agent/headless.py`、`docs/evaluation/harbor.md` 提供与 Harbor/Terminal-Bench 单任务执行适配；历史项目固定过 Harbor `0.23.0`。`docs/HANDOFF.md`、`docs/evolution/context_management.md` 记录的 `terminal-bench/make-mips-interpreter` 多次试跑 reward 都为 `0.0`。其中提高输出预算到 32768 后，运行约 32 轮、50 次工具调用，累计 Provider 报告 706,051 prompt、83,530 completion tokens，最终 `PROVIDER_OUTPUT_LIMIT`，没有生成目标可执行结果；只改执行策略 Prompt 后的单 Trial 约 37 轮/55 次工具调用、997,825 prompt/176,112 completion tokens，仍 reward 0；引入结构化近期文件记忆后的另一单 Trial 约 34 轮/50 次调用，仍没有完成目标代码生成。部分实验还出现 Provider timeout、依赖安装阶段失败和无 Token usage。

所以最能确定的结论不是模型哪组 Prompt 更强，而是：**当前 Agent 对某些复杂任务存在重复探索、迟迟不动手实现、单轮输出触顶的问题**；这几次试跑没有解决这一任务。把“少了几轮探索”包装成 Terminal-Bench 能力提升没有事实支持。Token 限制失败与工具调用异常是两个不同终止事件，应通过 Trace 的 `finish_reason`、真实 Provider usage 和 Verifier 结果分开审查。

## 9. 哪些历史数字不能使用

此前讨论过“平均轮次 26.3→19.7”“平均耗时 82.9→63.2s”。在目前阅读的远程 `docs/evolution/` 和 `eval_reports/` 中，尚未找到能够同时定位这些具体数据的两个完整 manifest、相同的任务范围、Provider/模型、Trial 分母与对应原始 Trace 的完整证据链。因此它们**仅列为历史待核数字**，不能写成正式 A/B，更不能与 `task_013/014` 的 Token 改造混为一次实验。

其他不合格结论包括：把 646 passed/4 failed 写成全部通过；把静态 contract/mutation test 通过当成真实模型任务成功；把 README 的“当前能力”当成已验证的真实部署结果；把已更换 Verifier 的前后报告按同一基准比较；把 `eval_result` 与 Agent 文本中 `SUCCESS` 或工具成功率混为同一指标。

## 10. 当前评测可信性边界与后续资料要求

远程版本确实保留了源代码、测试 Fixture、代码演进记录和若干 `eval_reports`。但是 `sandbox/eval_results/`、`benchmark/harbor/jobs/` 等原始运行目录往往受 `.gitignore` 忽略，不在可访问的远程 Git Tree 中；本次无法审查每一条原始动态模型请求与 Tool Trace。因此本篇对历史分数的定位准确说是“**已核查远程报告中的分子、分母、条件与公开错误说明**”，不是“重新完成了全部原始 Trial 审计”。建议保存本篇对应表格所需的运行 manifest、result、trace 到受控归档，避免未来同样难以还原。

Evaluation 体系最终在回答两个不同问题：**实现机制是否满足确定性状态不变量**（单元/独立进程故障注入）和**模型在固定真实任务上是否产生了所需业务结果**（Provider + 独立 Verifier）。这两个答案任何一方都不能替代另一方。必须同时报告版本、样本、环境、失败以及未测范围，文档才能长期可追溯。
