# 上下文成本治理——简历驱动追问链

## 0. 简历怎么写

推荐 bullet：

> **上下文成本治理：**针对测试日志和 Shell 输出直接回填上下文造成 Token 膨胀的问题，将超长 Tool Output 落盘并仅返回 Head/Tail 与可定位路径，结合窗口化读取、分层微压缩和 Tool Call 链完整性清洗控制上下文增长；两个长日志专项 Benchmark 均保持 5/5 完成率，Token 分别降低 66.6% 和 68.8%。

最希望面试官第一问：

> 你把长日志截断以后，如果真正的错误刚好在中间，不就把 Agent 搞瞎了吗？

---

# 一、第一问：为什么不能直接把 Tool Output 全塞回上下文？

## 30 秒回答

> Coding Agent 的工具输出和普通聊天不一样，尤其测试日志、编译日志、grep 结果可能一下几万甚至几十万字符。如果原样塞回 messages，后续每一轮模型都要重新携带这段历史，成本会累积放大，而且真正有用的信息往往只占极少部分。所以我没有简单截断丢弃，而是把完整输出持久化到 workspace 下的日志文件，只在当前 Tool Result 返回 Head/Tail、总行数、总字符数和文件路径；如果错误在中间，Agent 可以再用 search_code 或 read_file 精确读取那一段。

---

# 二、当前长输出文件化具体怎么做？

当前 `BaseTools.format_tool_output()` 的基本规则：

```text
输出 <= 40 行 且 <= 2000 chars
→ 原样返回

否则
→ 完整内容写入 .agent/logs/cmd_xxx.log
→ Tool Result 只返回：
   exit code
   总行数 / 总字符数
   完整日志路径
   前 10 行
   后 20 行
   提示使用 search_code / read_file 继续定位
```

这里有两个关键点：

1. **不是 destructive truncation**：完整输出还在文件里；
2. **模型有二次检索路径**：不是“看不到中间就算了”。

---

# 三、如果真正错误在中间怎么办？

这正是 `task_014_large_log_middle_debug` 专门验证的问题。

该任务故意让：

```text
Head 没有关键错误
Tail 也没有关键错误
只有中间某段日志有真正诊断信息
```

Baseline 直接携带整段日志；改造后第一次只得到 Head/Tail + file path，Agent 必须主动：

```text
search_code(saved_log, error pattern)
或
read_file(saved_log, start_line, end_line)
```

再定位中间错误。

结果：

```text
Baseline: 5/5
Refactor: 5/5

Token: 254.0k → 79.3k  (-68.8%)
Peak Turn Tokens: 24.3k → 7.8k  (-67.9%)
平均轮次: 14.8 → 13.8
```

所以这条机制不是“为了省 Token 把日志砍掉”，而是把一次性大块上下文改成**按需检索式上下文**。

# 四、另一个长日志 Case 的结果

`task_013_large_log_debug`：

```text
Baseline: 5/5
Refactor: 5/5

Token: 143.5k → 48.0k  (-66.6%)
Peak Turn Tokens: 18.5k → 5.7k  (-69.3%)
```

> 这不是证明“所有任务都能省 67% Token”。这是 long-output-specific Benchmark。

# 五、为什么返回 Head 10 + Tail 20，而不是别的比例？

不要把这个参数吹成实验全局最优。

当前它属于工程启发式：

```text
Head
→ 常见命令上下文、启动配置、测试环境信息

Tail
→ 常见异常汇总、失败测试名、最后 stack trace
```

为什么 Tail 比 Head 多：多数 CLI / test runner 会把最终失败摘要放尾部。

如果面试官问“为什么不是 20/20”：

> 当前没有做系统化 grid search，所以我不会说 10/20 是最优。真正关键的是“完整结果外置 + 可再次定位”，Head/Tail 只是第一屏摘要策略。后续如果 Benchmark 发现某类工具经常在特定区域产生高价值信息，可以按 Tool 做专门摘要，而不是统一调一个数字。

# 六、为什么不用 LLM 先总结日志？

因为“先总结”本身需要把完整日志送进模型，第一轮 Token 成本已经发生，而且总结可能丢失精确行号、错误码和罕见关键字。

当前方案：

```text
完整日志 → 本地文件
模型只看有限窗口
需要时 deterministic search / range read
```

优点：

```text
不需要额外模型调用
原始证据完整保留
能按关键字精确定位
不会因为摘要 hallucination 改写错误信息
```

LLM summary 更适合长会话语义压缩，不适合作为所有原始 Tool Output 的第一步。

# 七、长输出文件化和 Compressor 是一回事吗？

不是。

## Tool Output Fileization

发生在工具结果刚产生时：

```text
Tool output
→ 如果过大，立即落盘
→ 当前轮只进入有限窗口
```

目的是从源头阻止一次超大输出污染 Context。

## Microcompact / Full Compression

发生在历史消息已经积累以后：

```text
messages token 超阈值
→ 对旧 Tool Result 做 Stubbing
或
→ 对中间历史做完整总结压缩
```

目的是处理长期会话增长。

一句话：

> Fileization 是 ingress control；Compression 是 history lifecycle management。

---

# 八、Microcompact 是怎么做的？

当前 `Compressor.microcompact()` 是分层 Stubbing：

```text
保护：
system + 首条 user + 最近 6 条

Tier 1 重型输出：
bash / search_code / count_occurrences
→ 旧的大输出替换成短 stub

State Folding：
旧 TodoWrite
→ 只保留最新状态，旧状态替换 stub

核心资产：
read_file / edit_file 过长
→ 保留前 500 + 后 500，中间省略
```

为什么不是所有旧消息都直接 summary？

> Tool 消息除了内容还有结构关系；Coding Agent 经常需要保留“哪个 tool_call 对应哪个 tool_result”。粗暴删除可能直接破坏 Provider message contract。

---

# 九、Tool Call 链完整性为什么重要？

OpenAI 风格消息里：

```text
assistant(tool_calls=[id=abc])
→ tool(tool_call_id=abc)
```

必须闭环。

压缩时如果只删掉 Tool Result，却留下 assistant 的 tool_call：

```text
assistant says call abc
但没有 abc 的 tool response
```

Provider 可能直接返回 400，或者上下文结构不合法。

因此 Compressor 有两层清洗：

```text
_clean_tool_chains
sanitize_openai_messages
```

主要处理：

```text
孤立 tool response
缺少部分 tool responses
assistant 有 tool_calls 但响应全丢失
```

这点非常适合面试追问，因为它说明“上下文压缩”不是纯文本摘要，而是**带协议结构的消息图裁剪**。

# 十、为什么会有 Token 阈值压缩？

当前 Compressor 有：

```text
token_threshold
microcompact threshold ≈ 70% threshold
full compress > threshold
```

设计意图：

```text
接近 Context 上限前
→ 先用低损 Stubbing 降一轮

真的超过阈值
→ 再把早期 conversation middle 做 summary
```

这比每 N 轮固定压缩更合理，因为不同任务每轮增长速度差别很大。

但不要说“70% 是最佳值”，这是配置启发式。

---

# 十一、Full Compression 怎么避免丢掉当前任务关键上下文？

当前策略：

```text
保留最前 2 条
→ system + 初始任务背景

保留最近 15 条
→ 最近执行上下文

中间历史
→ summary
```

同时对 tail 的 Tool 链做闭环扩展和 sanitize。

这样做的假设是：

```text
最老的系统约束很重要
最近执行轨迹最重要
中间大量重复探索可以摘要
```

如果面试官问“会不会摘要错”：

> 会有风险，所以我不把 Full Compression 当无损操作。实际成本优化最显著的长日志 Case 主要来自 Tool Output Fileization，不需要依赖 LLM summary 才成立。Full Compression 更像超长会话的兜底机制。

---

# 十二、为什么不只靠模型 Context Window 变大？

因为 Context Window 变大不等于上下文成本消失。

问题包括：

```text
输入 Token 成本上升
每轮 latency 增加
长上下文注意力稀释
高价值信息被大量日志淹没
Prompt Cache 稳定性下降
```

所以 Context Engineering 的目标不是“塞得下”，而是：

> 只把当前决策需要的信息放进 active context，把可恢复的原始证据外置。

---

# 十三、为什么窗口化 read_file 也算 Context Governance？

早期 `read_file` 容易整文件读入。

后来支持：

```text
start_line
end_line
max_lines
```

如果不指定 end_line，默认 soft cap 200 行。

意义不是单纯工具更方便，而是让 Agent 能形成：

```text
先定位
→ 再读取局部窗口
→ 修改
→ 再局部验证
```

避免“大文件反复从头读”。

这和长日志外置其实是同一个思想：**retrieve what you need, not everything available**。

# 十四、你怎么证明没有因为压缩漏掉关键错误？

三个层次：

### 1. 结果正确性优先

必须先看 `verify.py` 是否通过，不允许因为 Token 下降就说“优化成功”。

### 2. 专门设计 middle-only Case

`task_014` 故意让关键错误只在中间，验证 Agent 能不能主动二次读取。

### 3. Trace 看工具路线

报告里会记录：

```text
Tool Call Sequence
Read Saved Log = yes/no
```

所以不仅看最后过没过，还能确认它是否真的使用了外置日志，而不是碰巧猜对。

---

# 十五、Context 压缩最容易犯的错误是什么？

至少准备这几个：

1. **只看 Token，不看成功率**；
2. 删除 Tool Result 后破坏 tool_call_id 链；
3. 每轮都重写历史消息，破坏 Prompt Cache；
4. 过早 summary，模型失去精确错误证据；
5. 截断后不给“怎么继续读取”的路径；
6. 所有 Tool 用同一种压缩策略；
7. 把近期执行轨迹也压掉，导致 Agent 重复探索。

---

# 十六、项目里一个很典型的“优化反而不好”案例

历史上曾给 TodoWrite 做复杂状态维护和压缩包装，但 Trace 发现模型会过早在 Todo 中规划 `verify.py`，反而把不必要验证固化成计划。

演进大概是：

```text
发现 verify.py 过度生成
→ 修改 Todo 描述
→ 无明显变化
→ 给验证工具加更多语义包装
→ 仍然过度验证
→ 调整 Todo 消息写回方式
→ 轮次 / Token 有下降，但行为仍存在
→ 最后直接从 Tool Schema 禁用 TodoWrite
```

这个 Case 很适合说明：

> Context / Tool 设计不能靠“给模型更多指导”无限修补，有时减少工具能力反而比增加 Prompt 约束更有效。

# 十八、最后背这一段

> mini-claude 的 Context 优化不是简单“把历史做摘要”。我主要分两层：第一层在 Tool Output 进入上下文之前做 ingress control，超大日志完整落盘，只返回 Head/Tail、统计信息和可重新定位的路径；第二层才是历史生命周期管理，对旧 Tool Result 做分层 Stubbing，必要时再做完整会话压缩，同时保证 tool_calls 和 tool responses 的协议闭环。两个专门的长日志 Benchmark 都保持 5/5，其中一个还故意把唯一有效错误放在日志中间，验证 Agent 能通过 search/read 二次定位；Token 最终分别下降 66.6% 和 68.8%。
