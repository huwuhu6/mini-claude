整理日期：2026-10-22。

实施进展（2026-10-22）：本文以下问题表保留审查基线事实，不表示全部仍未处理。已修复 Run ID 会话绑定、同进程恢复校验、文件目标漏检与空快照归档，增加结果/效果分类及只读文件核验证据。提交前独立审计另发现嵌套 Registry 异常误判 NONE，现已用执行标记、原因码白名单和 Store 阶段校验修复。实际提交、逐项 NONE 证明、红绿对照及 Windows/Linux 验证统一见 [工具与 Runtime 演进](evolution/tool_registry.md) 的 2026-10-22 阶段；自动解除 UNKNOWN、Shell 核验和重试出口尚未实现。

审查代码基线：`40638955aca983bd840313c626d94616333f5e72`（`feat: 完善本地会话恢复、授权交互与终端展示`）。该实现及文档收尾提交 `a227f0b` 已快进整合并推送到 `main`；本报告在从该 main 创建的 `checkpoint_review` 分支单独维护。本文结论针对该实现基线，后续代码变化需要重新核验。

本文整理本次对话已经提出的调查结论，去重后共 6 类、24 项。它包含已复现的功能缺陷、结构性问题、待测量问题和能力边界；不能将所有条目都视为必须立即补齐的功能。

调查以当前实现和确定性测试为依据，并对照 Claude Code、OpenHands、LangGraph、Temporal、MCP 等公开技术资料。没有依据项目历史演进文档预设结论，没有修改实现。

## 一、已复现的功能缺陷

| 编号 | 问题 | 可能造成的结果 |
| --- | --- | --- |
| 1 | 实际操作目标的变化可能漏检：工作区摘要忽略 `.git`、`build` 等目录，也不覆盖额外授权目录 | 用户批准后修改目标，恢复执行仍可能用旧内容覆盖新修改 |
| 2 | 同进程继续与新实例恢复的校验不一致 | 同一暂停任务，新实例拒绝执行，原实例却能继续覆盖已变化的文件；已在 checkpoint-only API 模式复现 |
| 3 | 用 Run ID 加载已完成历史，没有同步切换会话身份 | A 的消息被加载到 B 的身份下，新 Run 保存到错误会话；加载含 UNKNOWN 的历史时，还可能丢失执行阻断 |
| 4 | `/new` 没有清理完整的会话上下文 | 消息已清空，但旧 `agent_note` 仍进入新会话的模型请求，造成上下文污染 |
| 5 | 首次快照前留下的 started Run 没有完整处理出口 | 初始化窗口崩溃后，任务无法恢复，也无法通过当前 Agent 入口归档；选中后又阻止新建会话 |
| 6 | 普通执行失败没有充分表达副作用不确定性 | 工具效果已发生，响应却超时；当前记录为执行失败，模型下一轮重新请求时，效果可能发生两次 |

第 6 项中，Journal 的 COMPLETED 表示调用结果已记录，不等于业务成功，也不等于确认没有不确定副作用。UNKNOWN 不能只通过“崩溃后发现 RUNNING”产生。

## 二、恢复流程与工具语义的缺口

| 编号 | 问题 | 当前影响或后续风险 |
| --- | --- | --- |
| 7 | UNKNOWN 缺少核验与处理闭环 | 已有查看和归档入口，但没有通用的结果确认、受控重试或补偿协议 |
| 8 | 查看历史、继续原执行、重新规划、历史重执行等语义没有充分分开 | 临时 Provider 故障使 Run 终结后，即使 Provider 恢复，resume 也只返回旧错误；缺少保留进展后的明确处理方式 |
| 9 | 全工作区摘要容易让无关变化阻断任务，审批失效后又缺少顺畅出口 | 新增无关日志就能使批准失效；恢复原内容后，原批准仍无法使用，只能转向其他人工处理 |
| 10 | 工具缺少可供 Runtime 使用的执行与恢复声明 | 无法系统地区分只读、幂等、依赖幂等键、条件执行、可核验和可补偿等能力 |
| 11 | 缺少同一逻辑操作与多次执行尝试之间的明确关联 | 模型换一个 Tool Call ID 重新发出操作后，原有防重复启动机制无法自动判断它是不是同一次业务操作的重试 |

工具能力声明与本次调用是否可以恢复需要分别判断。结果记录还需要实际目标、前置条件、外部资源标识、执行回执和核验证据；仅增加布尔字段不足以支持安全恢复。

核验结果也应区分：原操作确认完成、目标状态已满足但归属不明、确认未执行、仍在执行、状态冲突和证据不足。目标存在不能直接证明原调用成功；目标不存在也未必证明原调用未执行。

## 三、兼容性与上下文恢复问题

| 编号 | 问题 | 影响 |
| --- | --- | --- |
| 12 | 源码哈希兼容性判断过于粗粒度 | 注释、格式或日志文字变化也可能阻止未完成 Run 恢复；数据库结构升级成功，也不代表运行快照语义兼容 |
| 13 | 源码身份不能完整代表执行语义 | 已用同源码、不同捕获值的闭包复现：工具契约相同，实际执行结果不同 |
| 14 | 恢复时哪些上下文应继承、刷新或固定，规则不完整 | 已验证 system prompt 可以变化，而兼容性字典保持相同；恢复后的下一次模型请求使用新提示 |

不是所有上下文变化都应被禁止。原调用目标和参数需要保持一致；当前权限与凭据可用性需要重新检查；文件观察和环境探测需要刷新；提示、模型和工具配置需要明确允许变化的范围并记录变化。

## 四、历史、存储与性能问题

| 编号 | 问题 | 影响与证据范围 |
| --- | --- | --- |
| 15 | 当前上下文与权威原始历史的分工不明确 | 每个 Run 的当前快照不断更新；压缩产物只保存摘要，不能保证恢复被摘要替代的原文。诊断日志允许记录失败，不能直接充当权威历史 |
| 16 | 数据库绝对路径被当作归属身份的一部分 | 已复现：干净关闭后复制数据库到新文件名，数据库结构能打开，但原 Run 无法加载，限制备份恢复、迁移和副本检查 |
| 17 | 每次推进存在多层全量处理 | 重复扫描工作区、读取源码、序列化快照，并在事务中重新读取和哈希整个执行日志；调用量增长后，累计成本可能接近二次增长 |
| 18 | 缺少专项性能对照数据 | 尚不能量化内存模式、Checkpoint-only、Checkpoint＋HITL 各自的增量成本，以及不同调用数量和结果大小下的存储成本 |

第 15 项是“完整历史缺少保证”，不是所有原文一定丢失；旧快照或日志可能另有部分记录。第 17 项是代码复杂度分析，没有大仓库实测耗时。第 18 项不等于缺少恢复测试，当前已有真实进程崩溃、提交失败和并发恢复等确定性验证。

## 五、架构耦合与并发保护范围

| 编号 | 问题 | 影响 |
| --- | --- | --- |
| 19 | 恢复规则分散在多个模块，并依赖彼此内部实现 | Agent 协调快照、锁、审批、会话和终结；Store 理解消息与批次协议；ApprovalStore 直接使用 Store 私有事务接口。修改状态转换时容易遗漏其他入口 |
| 20 | Run／Conversation 锁不提供跨会话资源冲突保护 | 已复现两个会话都消费批准并进入 RUNNING，随后先后覆盖同一文件，两次调用均正常完成 |

第 20 项需要先确定工程约定：是否允许最后一次写入覆盖之前结果，还是要求隔离工作区、资源锁或条件写入。它是已经验证的保护边界，不将所有并发写入一概视为 bug。

审批消费与启动调用必须继续保持同一事务；不能为了拆模块而拆成两个独立提交。

## 六、明确的能力边界

| 编号 | 当前边界 | 需要注意什么 |
| --- | --- | --- |
| 21 | 不同入口默认行为不同 | 普通 CLI 默认启用审批和持久化；直接构造 Agent 与当前 headless 入口默认未启用，`--no-hitl` 显式关闭 |
| 22 | 持久化模式主要支持主 Agent 的顺序前台工具批次 | 后台任务和 SubAgent 在该模式下被明确拒绝，尚无对应执行栈恢复协议 |
| 23 | 直接调用底层 Registry 或工具，不自动获得相同持久化保证 | 新增执行入口时必须确认是否经过统一调度、审批和执行日志边界 |
| 24 | 当前主要面向本机可信数据库 | 不应将其理解为已提供跨机器租约、完整外部副作用事务、数据库加密或通用自动补偿 |

这些边界不都属于当前必须修复的缺陷，应按实际使用需求扩展。

## 问题依赖与取舍

| 单独修改某一项 | 容易出现的另一端问题 | 需要一起考虑 |
| --- | --- | --- |
| 放宽工作区校验 | 旧调用覆盖新状态 | 目标依赖、资源版本、冲突检测 |
| 自动重试失败工具 | 重复外部效果 | 副作用确定性、逻辑操作身份、核验能力 |
| 强化源码一致性 | 小修改后无法恢复 | 契约版本、兼容范围、重新规划入口 |
| 为性能减少保存次数 | 扩大结果丢失和不确定窗口 | 必须同步保存的执行事实与可重建快照的分工 |
| 开放更多并发执行 | 不同任务互相覆盖 | 调度范围、资源隔离、条件写入 |
| 放开数据库迁移或克隆 | 两个副本重复执行原操作 | 逻辑身份、迁移规则、副本执行资格 |
| 持久保存更多历史 | 存储和扫描成本增长 | 增量保存、保留策略、证据引用关系 |

建议先修第 1—6 项明确缺陷，同时确定第 7—14 项基础约定；再据此调整第 15—20 项的存储与模块边界。第 21—24 项按实际需求扩展。
