### Description

本次开发在 `fix/output-limit-recovery` 分支完成，开发基线为 `52440ca`。本文按实际排查顺序记录问题、两轮修复、真实试跑和最终验收。当前配置和使用方式见 README；本文保存设计原因、实验结果和最终取舍。

## 一、最初遇到什么问题

长任务中，模型可能把单次输出额度用在思考上，还没有返回完整答案或完整工具调用，请求就以 `finish_reason=length` 结束。这里的 `length` 是服务端返回的停止原因，表示本次生成到达长度限制。

当时 Runtime 已经能识别输出截断，也会拒绝执行截断响应中的工具。但它只能以 `PROVIDER_OUTPUT_LIMIT` 停止整个任务：模型还有机会通过调整参数返回完整响应，运行却已经结束。

此前尝试单纯提高输出额度，没有消除这个问题。原因是输出额度变大不代表模型会更早结束思考；一直增加额度还会增加每次失败的消耗。因此本次目标是：识别截断后，在有限次数和预算内调整参数，重新生成当前响应，获得完整响应后继续原任务。

## 二、第一轮修复：重新生成当前响应，并限制恢复消耗

### 1. 只重试当前模型请求

恢复使用截断前可信的输入消息，不把截断正文、思考或残缺工具参数追加回历史。截断响应中的整批工具调用都不执行，已经执行完成的旧工具也不重放。

拿到完整响应后，仍进入原有工具参数检查、权限检查和人工审批流程。恢复机制没有另外开一条工具执行通道。

### 2. 根据部署声明调整参数

思考强度不是所有模型共有的能力，档位名称也不统一。配置通过 `supported_reasoning_efforts` 声明当前部署支持的选择，按从低到高排列；Provider，也就是对接模型服务的代码，负责选择前一个档位。Runtime 不根据模型名称猜测档位。

本次百炼部署为 `deepseek-v4-flash-0731`，使用 `[low, high, max]`，初始为 high。发生截断时优先降低思考强度；不能再降时，再尝试增加本次输出上限。未声明强度能力的模型不发送 `reasoning_effort`，仍可通过调整输出长度恢复。

公共配置接受不同模型自己的档位名称，没有把所有模型限制在 low、medium、high、max 这几个词里。也没有增加自动升档、切换模型或关闭思考模式。

### 3. 次数与 Token 预算共同约束恢复

仓库最终使用的参数为：

| 配置 | 数值 | 含义 |
|---|---:|---|
| 正常输出上限 | 8192 | 正常模型请求的输出额度 |
| 恢复输出上限 | 32768 | 额外恢复请求可调整到的最大输出额度 |
| 每轮恢复次数 | 2 | 一轮模型响应最多额外请求两次 |
| 同任务恢复次数 | 4 | 一个用户任务内最多额外请求四次 |
| 恢复 Token 预留总额 | 262144 | 额外恢复请求累计可预留的额度 |
| 上下文安全余量 | 2048 | 估算剩余空间时预留的余量 |

额外请求发出前，按“估算输入 Token + 本次允许的完整输出额度”预留预算。服务报告的实际用量超过预留时补记差额；少用、缺少用量或者中断时不退还预留，防止反复重启获得新的额度。该预算专门约束额外恢复请求，正常请求和压缩摘要另行记录用量。

次数、预留量和当前尝试随 `RunState` 保存。`Run` 是从一次用户请求开始，经过模型调用、工具执行和审批，直到该次任务结束的运行；不是单独一次模型请求。新进程恢复原 Run 时不能重置这些计数。

### 4. 输出空间不足时复用现有压缩

发送请求前估算完整输入，包含消息、系统提示和工具定义。如果配置的上下文窗口装不下计划输出，尝试现有历史压缩，再计算可用输出空间。没有空间、参数已无法调整或者恢复预算用完时，明确停止。

本地使用 `cl100k_base` 估算，它不是 DeepSeek 的专用分词规则；缺少分词库时退回字符数估算。当前窗口来自配置，没有在初始化时自动查询服务。服务端直接拒绝上下文超长请求后的自动压缩重试，留作后续上下文管理工作。

## 三、第一次真实测评：恢复生效，但下一轮又回到 high

按用户要求，先降低额度，再运行 Terminal-Bench 第一题 `make-mips-interpreter`。Oracle，也就是基准任务提供的参考实现，先得分 1.0，确认环境和评分流程可用；随后真实 Agent 只跑一次，任务重试为零。

使用 DashScope / `deepseek-v4-flash-0731`、流式请求、温度 0.7，正常输出 8192，恢复上限 32768。实际所有请求都使用 8192，没有靠扩大输出额度取得恢复。

| 项目 | 第一次真实试跑结果 |
|---|---|
| 模型轮次 / 请求数 | 44 轮 / 48 次请求 |
| 工具调用数 | 70 次 |
| high 截断 | 第 36、37、40、42、44 轮，共 5 次 |
| 额外恢复 | 前四次改为 low 后得到 `tool_calls` 响应 |
| 停止原因 | 第五次截断时，任务内四次恢复额度已用完 |
| 输入 / 输出 Token | 1327658 / 109682 |
| 四次额外恢复请求用量 | 合计 197761 Token |
| Agent 耗时 | 约 29 分 24 秒 |
| 任务得分 | 0.0，目标程序和图像产物未生成 |

第一次 low 响应的工具参数 JSON 不完整，被既有校验拒绝，没有执行。后三次恢复分别执行了 2、1、1 次合法工具调用。这直接验证了截断后的参数调整、重新生成、工具检查和继续执行。

同时，Trace 暴露了一个设计缺陷：降档只作用于当前轮。当前轮恢复成 low 后，下一轮正常请求又从配置中的 high 开始，重复触发截断，最终耗尽四次恢复额度。

因此第二轮修复不继续加额度，而是让同一任务记住已经接受的降档结果。

## 四、第二轮修复：同一任务保留降档结果

新增 `persist_effort_for_run`，仓库默认配置显式开启。只有恢复请求返回完整响应后，才把较低强度保存到 `RunState.output_limit_effective_effort`，后续模型轮次沿用它。

例如第一次 high 截断、low 恢复成功，此任务后面的正常请求继续使用 low，不再每轮回到 high。用户发起新的任务时，重新从配置的 high 开始。同一 Run 的暂停、审批和进程恢复仍保留已经接受的强度。

只保留思考强度，不保留临时放大的输出上限。例如恢复请求从 8192 增至 16384，下一正常轮仍从 8192 开始，避免一次恢复永久扩大后续请求额度。

请求报错、再次截断和根本没有发出的请求，都不会提交候选档位。快照同时保存降档状态，并核对 Provider、部署地址和参数声明，恢复时不能借旧快照更换部署或退回预算。最终独立快照、Checkpoint、审批快照版本分别为 10、11、12，保留旧版本读取和原有执行校验。

## 五、第二次真实测评：跨轮保留开始生效，外部超时暴露记录缺口

第二次仍跑同一道题，固定数据集和任务版本，安装源码与配置均核对指纹。输出、次数和 Token 预算保持不变，只开启同任务降档记忆。

| 轮次 | Session 保存的恢复参数 | 后续行为 |
|---|---|---|
| 27 | low / 8192 | 随后进入第 28 轮 |
| 38 | low / 16384 | 随后进入第 39 轮 |
| 39 | low / 16384 | 请求启动后达到外部时间上限 |

第 38、39 轮直接采用 low / 16384，符合“已在最低强度，转而增加输出长度”的路径，支持任务内降档记忆生效。此次进入第 39 轮，共记录 63 次工具调用，Agent 在 1800 秒上限被 Harbor 停止，总耗时约 32 分 25 秒。目标程序仍未生成，任务得分 0.0。

这次又发现了一个独立问题：完整 Trace 在任务结束时写出，外部超时后没有最终 Trace。原 Session 只保存恢复启动事件，无法逐一核对全部模型请求的参数、结束原因和用量。因此下一步补请求记录，不继续增加额度，也不修改任务推进策略。

## 六、补齐逐请求记录，让超时前的请求仍可检查

在现有 Session JSONL 中增加 `provider_request_started` 和 `provider_request_finished`。每次主模型请求和压缩摘要请求都有独立 `request_id`，记录 Run、轮次、尝试序号、来源、参数、停止原因和服务实际报告的用量。

开始事件在调用前落盘，完成事件在返回或报错后落盘。只有开始、没有完成的请求保留为未确认完成，用量保持未知。明确零、缺失字段和部分用量分别保存，不用零填补丢失的实际数据。

记录只保存检查恢复行为所需的信息，不额外复制提示正文、响应正文、私有思考或密钥。日志写入失败不改变恢复决策；Session 是诊断记录，执行状态和预算仍由原 RunState / Checkpoint 管理。

进程强杀测试实际产生两次已完成请求，再启动第三次阻塞请求，由父进程直接终止子进程。最终没有完整 Trace，但 Session 保留了三条开始、两条完成，前两次模拟用量合计 8125，第三次仍为未知。这验证了外部超时下的新记录方式。

## 七、最终对照：确认修复解决了重复截断

最后使用真实 OpenAI SDK、实际 Provider 和完整 Agent 工具循环，对接本地模拟服务。服务固定为：high 返回 length；low 返回六轮合法工具调用，然后正常结束。三组保持同样的输出上限和最多四次恢复，只改变恢复开关和任务内降档记忆。

| 设置 | 模型请求数 | 额外恢复次数 | 完整工具轮次 | 结果 |
|---|---:|---:|---:|---|
| 关闭恢复 | 1 | 0 | 0 | 首次截断后结束 |
| 仅本轮降档 | 9 | 4 | 4 | 每轮重回 high，第五次截断时停止 |
| 同任务保留降档 | 8 | 1 | 6 | 后续沿用 low，执行六轮工具后正常结束 |

流式和非流式各执行三组，结果相同。模拟对照中，恢复次数从 4 次降至 1 次，并从中途耗尽额度变为正常结束。检查覆盖实际请求参数、重试前后输入、工具真正执行的次数，以及截断工具始终不执行。

另验证不支持思考强度的模型：输出从 8000 调整至 16000 后恢复，下一正常轮回到 8000，没有发送思考参数。预算边界测试使用估算输入 100、输出上限 8000：预留总额 8099 时阻止请求，8100 时允许一次，确认边界按完整预留量执行。

### Decision / Limitation

本分支完成输出截断恢复：有可用参数和预算时重新生成完整响应；同任务保留已经生效的降档；预算耗尽时停止；进程超时前的已完成请求可以独立查看。

保留当前较小额度和单向降档，不增加自动升档、模型切换、复杂评分控制器，也不对单道 Benchmark 添加特殊规则。模型持续调查而没有实现程序的问题另行处理。

后续可以按 Provider 支持情况查询模型窗口、输出上限和思考能力；查不到时使用配置。接近窗口边界时，也可接入服务端 Token 计数。这些属于后续能力，不影响本次修复收尾。
