# edit_file 演进记录

这份文档只记录文件编辑工具在可靠性、定位能力和 Token 成本之间的取舍。

## 1. 从单次替换到批量事务

### 问题

单次字符串替换难以支持一个任务中的多个修改；如果前面的修改已经写盘，后面的匹配失败可能留下半完成状态。

### 演进

在 `a203dd6` 中，`edit_file` 增加批量编辑，并在写盘前逐一验证所有 search 片段。任何一处验证失败时，整个编辑事务取消，避免部分修改污染 workspace。

同时对 CRLF/LF 和行尾空格做内容归一化，降低跨平台换行差异导致的误匹配。

## 2. 从精确定位到受控的近似定位

### 问题

LLM 提供的行号可能只接近目标位置；完全依赖精确行号会导致本来可执行的编辑失败，但无约束的模糊匹配又可能误改相似代码。

### 最终方案

在 `bee2c1e` 中增加近似行号定位，同时保留 search 内容匹配、匹配唯一性和上下文范围约束。定位能力增强，但编辑仍必须落到可验证的代码片段上。

## 3. 写盘安全与载荷约束

在 `0c17d06` 中增加上下文长度和编辑载荷大小限制，避免超大请求绕过工具边界。当前实现使用临时文件加 `os.replace()` 完成原子替换，降低磁盘半写入风险。

## 当前结论

`edit_file` 的核心原则是：先验证、后提交；批量操作整体成功或整体失败；允许适度定位容错，但不牺牲匹配可解释性。
