# 下一步开发与命令行版本说明

这份文档用来记录两件容易混淆的事情：

1. 如何确认 `mini-claude` 命令使用的是仓库里的最新代码。
2. 如何在真实项目中主动发现 Agent 的问题，再决定是否增加 Benchmark。

## 一、这次发现了什么

之前仓库里的 `pyproject.toml` 虽然声明了命令入口：

```text
mini-claude = "cli.entrypoint:main"
```

但电脑实际执行的命令来自：

```text
D:\python3.12.1\Scripts\mini-claude.exe
```

这个 Python 环境里原来安装的是一份普通复制版。它的 `agent/mini_claude_agent.py` 文件日期是 2026-05-10，仓库里的源码日期是 2026-08-02，文件大小也不同。因此，虽然安装记录指向本仓库，修改仓库代码后，命令仍可能继续运行旧副本。

## 二、已经做了什么修复

已经在真正执行 `mini-claude` 命令的 Python 3.12 环境中执行了 editable 安装：

```powershell
D:\python3.12.1\python.exe -m pip install -e . --no-deps
```

editable 可以理解为“只安装入口和路径，不再复制一份源码”。现在命令启动时会直接加载：

```text
D:\02_study\code\AgentProject\mini-claude\src\agent\mini_claude_agent.py
```

以后修改仓库源码，重新打开命令时就会使用最新代码，不需要每次重新安装。

## 三、以后如何自己确认

在任意目录运行下面的命令：

```powershell
Get-Command mini-claude
```

确认它指向预期的 `Scripts\mini-claude.exe`。然后运行：

```powershell
D:\python3.12.1\python.exe -c "import agent.mini_claude_agent; print(agent.mini_claude_agent.__file__)"
```

输出应该包含：

```text
D:\02_study\code\AgentProject\mini-claude\src\agent\mini_claude_agent.py
```

如果输出变成 `Lib\site-packages\agent\...`，说明又变成了旧的普通安装，需要重新执行 editable 安装。

## 五、Progress-aware Failure Governance（开发分支）

在 Anti-Loop Benchmark Freeze `7648e64` 上，DEV ×3 基线显示：旧运行时能够识别一部分重复失败，但仍会把可恢复的权限错误提前终止，也无法识别“工作区一直变化、业务状态却 A/B 振荡”的情况；遇到未解决阻断后，模型还可能直接用普通文本宣布完成。

本轮在 `feat/progress-aware-governance` 分支增加独立的 Progress Governance 层。LoopGuard、Failure Intelligence、WorkspaceStateGuard 及其阈值继续作为证据生产器和安全网，不由 Benchmark case 或语言名称驱动。新层组合 Action、Observation、Workspace State、Failure/Blocker 和历史进展，提供可解释的 `ALLOW`、`WARN`、`REPLAN`、`BLOCK_COMMAND`、`TERMINATE` 决策。

主要设计包括：

- `ObservationNormalizer` 去除 ANSI、绝对工作区路径、临时路径、时间和耗时噪声，同时保留 `5 failed → 3 failed → 1 failed` 这类有意义的数字变化。
- `ProgressTracker` 只有在语义观察或失败状态发生变化时，才把 workspace mutation 作为 Progress Evidence；单纯 diff 不算进展，并检测重复的 2/3 周期状态振荡。
- `BlockerLedger` 维护 `OPEN → MITIGATED → RESOLVED/TERMINAL` 生命周期；单个 permission、network、package 或 command 错误先是证据，不再自动结束整个任务。无关的 `echo success` 不能关闭阻断。
- `CompletionGuard` 在存在 unresolved blocker 时拦截一次无工具的完成声明，要求可执行验证或明确报告阻断；没有恢复证据的第二次声明进入有界终止路径，合法 fallback 在相关成功证据后仍可完成。

这套设计的合成不变量先于 Benchmark 调参验证。基线与 Candidate 的真实 DEV ×3 对比仍必须使用同一冻结 suite hash；若 Provider 产生 `INFRA_ERROR`，该 Trial 只进入基础设施分母，不计入治理指标。

注意：电脑上有多个 Python。`py` 命令当前可能使用 Python 3.14，而 `mini-claude` 命令使用 Python 3.12。评测命令和 Agent 命令不一定使用同一个解释器，排查问题时要先确认这一点。

## 四、真实使用时怎么主动发现问题

不要一开始就急着增加 Benchmark。先在真实项目里记录 Agent 做错的事情，只有当同类问题出现两次或以上，才值得沉淀成 Benchmark。

### 1. 多文件修改

让 Agent 做一个真实的小重构，例如：

```text
把 UserService 的 user_id 参数改成 uid，要求同步更新 controller、service、测试和调用方，但不要修改数据库层其他旧接口。
```

重点观察：

- 是否漏改某个调用方。
- 是否误改了不在范围内的旧接口。
- 是否只改函数签名，没有改函数体。
- 是否为了确认结果反复读取相同文件。

这类问题已经被 `task_006_cross_file_drift` 覆盖，但真实项目可以提供更复杂、更接近面试讨论的版本。

### 2. 不同平台命令

在 Windows 项目中提出需要检查代码、运行测试、查看目录的任务，观察 Agent 是否混用 Linux 命令：

```text
检查这个项目的测试入口，运行最小范围的测试，并解释失败原因。
```

重点观察：

- 是否错误使用 `grep`、`find`、`cd /d` 或 Linux 管道写法。
- 是否知道当前 Shell 实际是 CMD 还是 PowerShell。
- 命令失败后是否换成当前平台可用的方式。
- 是否因为一次命令失败就进入重复重试。

如果同一种平台错误重复出现，可以增加一个专门的环境适配 Benchmark。

### 3. 验证和停止时机

给 Agent 一个很小、容易确认的任务，例如只修改一个常量或一个函数，然后观察：

- 是否完全不验证。
- 是否使用合适的最小验证。
- 是否在已经有足够证据后继续重复搜索、计数和编译。
- 是否把评测脚本当成工作目标，而不是把代码行为当成工作目标。

这类观察可以帮助继续优化 `count_occurrences` 的使用策略和过度验证问题。

### 4. 失败后的恢复

制造一个安全的失败，例如让测试命令返回明确的断言错误，观察 Agent：

- 能否读懂错误真正指向的文件和行。
- 会不会只重复运行同一条失败命令。
- 会不会因为测试失败就修改测试本身。
- 修复后是否重新运行最小必要验证。

出现稳定重复模式后，可以增加“错误归因和恢复策略”Benchmark，而不是单独为每条错误消息写用例。

## 五、当前推荐顺序

当前 `task_006` 和 `task_012` 已经验证有效，不需要马上继续扩充相同类型的重构任务。推荐顺序是：

1. 先用真实项目测试平台命令适配和失败恢复。
2. 记录至少两次真实失败，再设计一个最小 Benchmark。
3. 用 3 次重复运行确认新 Benchmark 既能测到问题，又不会只是在测随机性。
4. 最后再根据 Trace 判断是否需要改 Agent，而不是看到某一次多用了几轮就立刻改代码。

Benchmark 的目标不是越多越好，而是每个用例都能回答一个明确问题：Agent 在什么条件下会失败，修改后是否真的变好了。

## 六、本轮运行目录和控制台改造

### 先看清楚这些目录分别做什么

- `.traces`：每个任务的运行记录，里面有轮数、工具调用、错误、Token 和最终状态。Benchmark 和问题排查都依赖它。
- `.transcripts`：上下文太长时，系统把旧对话压缩成摘要后保存的文件。没有发生压缩时不应该有内容。
- `.tasks`：`/task` 命令创建的任务文件，支持任务状态和依赖关系持久化。
- `.team`：队友信息文件。项目中目录名是 `.team`，不是 `.teams`。
- `.inbox`：队友之间的消息文件。
- `logs/agent.log`：程序内部日志，记录工具执行、异常、循环防护和 Trace 写入情况。

这些功能目前都被源码实际使用，因此没有删除对应逻辑。之前的问题是 Agent 一启动就创建多个空目录，即使用户从未使用任务、队友或上下文压缩。

### 本轮修改

- `.tasks`、`.team`、`.transcripts` 改为第一次真正写入时才创建。
- `.traces` 保持启动时创建，因为每次任务都需要写入追踪文件。
- 日志不再使用 `StreamHandler` 输出到控制台，所以工具命令、循环防护和内部模块日志不会再和 Agent 的回答混在一起。
- `logs/agent.log` 改用轮转文件：单文件最多约 5MB，保留 3 个旧文件。
- 修复多次在同一进程初始化 Agent 时可能复用旧日志文件的问题。
- REPL 去掉“代理：”前缀，启动和回答显示更接近普通聊天界面。

### 怎么判断日志是否正常

正常使用时，控制台只应该看到启动提示、输入提示和 Agent 回答。出现问题时去工作区的 `logs/agent.log` 查看完整上下文：

1. 先看时间，确认是不是本次运行。
2. 再看模块名，例如 `agent.mini_claude_agent`、`core.loop_controller`。
3. 重点找 `WARNING`、`ERROR`、`CRITICAL`。
4. 如果是工具问题，再看同一时间附近的命令和结果。

日志用于调试，`.traces` 用于还原一次任务和做 Benchmark 分析，两者不是重复文件。

## 七、控制台可见性与流式输出

上一轮为了避免日志污染界面，把所有日志都从控制台移除了。但这样也把 Agent 正在做什么一起隐藏了，用户只能长时间等待最后答案，这是不合理的。

### 本轮处理

控制台现在显示四类简洁信息：

- `分析中 · 第 N 轮`：Agent 正在进行第几轮模型调用。
- `↳ 工具 ...`：准备调用哪个工具、目标大致是什么。
- `✓ / ✗ / !`：工具成功、失败或被安全策略拦截。
- 最终答案：用单独的 `mini-claude` 标签和颜色显示，和用户输入区分开。

终端支持颜色时，用户输入使用青色，Agent 标签使用蓝色，工具使用黄色，成功使用绿色，错误使用红色；不支持颜色时自动退化为普通文本，也可以用 `NO_COLOR` 关闭颜色。

### 日志内容

日志不再只保留工具结果摘要，而是记录：

- 用户完整输入。
- 每轮 LLM 调用开始和结束信息。
- 模型返回的行动说明。
- 工具名称、完整参数和完整结果。
- 重复调用、参数解析失败、循环拦截、熔断和运行时异常。

控制台只显示适合人看的进度，日志保留适合调试的细节，两者职责不同。

### 流式输出为什么单独做

当前 Provider 明确使用 `stream: false`。要支持真正的流式输出，需要同时处理：

1. 普通文本逐片段显示。
2. 工具调用参数逐片段拼接，不能把半截 JSON 当成完整工具参数。
3. DeepSeek/OpenAI 风格和 Anthropic 风格的事件格式差异。
4. 流式请求中断、重试、Token 统计和 Trace 记录。

因此本轮先提供真实的工具进度，下一轮再改 Provider 的流式接口和 Agent 的增量解析。现在没有把“分析中”伪装成模型逐字输出。

## 八、修正“日志安静但界面失明”

上一轮把日志从控制台移除后，界面确实变干净了，但副作用是用户看不到 Agent 是否正在分析、调用了什么工具、工具是否成功。这是错误的取舍。

本轮重新分开两种信息：

- 控制台：只显示人真正需要知道的进度，例如第几轮分析、工具名称和目标、成功/失败/拦截、最终回答。
- 日志：记录完整的用户输入、模型行动说明、完整工具参数、完整工具结果、重复调用、参数错误、循环拦截、熔断和异常。

控制台使用颜色区分用户输入、Agent、工具和错误；没有颜色能力的 Windows 终端会退化为普通文本。装饰符号使用 ASCII 形式，避免旧版终端因编码问题崩溃。

这里的“分析中”表示一次模型调用正在进行，不等于把模型隐藏的完整思维过程打印出来。当前先显示可验证的行动进度，真正的逐 Token 流式回答留到 Provider 流式接口改造完成后处理。

## 九、会话记录和运行时目录迁移

### 为什么不继续使用普通 `.log`

普通日志把不同会话、不同模块的内容混在一起，查一次 Agent 行为时需要靠时间戳猜测上下文。本轮改成“一次启动一个 JSONL 文件”：每一行是一个事件，至少带有时间、会话 ID 和事件类型。这样以后可以同时保存多个会话，也方便脚本按 `type`、工具名或失败状态筛选。

JSONL 是详细记录的来源；控制台不是日志替代品。控制台只显示适合人快速阅读的进度，JSONL 保留完整的用户输入、模型动作说明、工具参数、工具结果、循环拦截、熔断和异常。

### 运行时文件放在哪里

默认根目录是 `D:\02_study\code\mini-claude-project-data`，每个工作区单独使用一个带短哈希的项目目录，避免两个同名项目互相覆盖。项目目录下面再按用途分为：

- `sessions/`：聊天记录和运行时事件 JSONL。
- `traces/`：任务级 Trace，继续作为 Benchmark 分析的标准输入。
- `tasks/`、`team/`、`inbox/`：任务、队友状态和队友消息。
- `transcripts/`：上下文压缩后留下的摘要。

也可以用环境变量 `MINI_CLAUDE_DATA_DIR` 指定另一处数据根目录。这样工作区本身不会再因为启动 Agent 而出现 `.trace`、`.team` 等运行时目录。

### 调试入口

不需要再次启动模型即可查看最近一次会话：

```powershell
mini-claude path/to/project --debug latest
mini-claude path/to/project --debug errors
mini-claude path/to/project --debug flow --session <session_id>
```

`latest` 看完整流程，`errors` 只看警告、异常、工具失败和拦截，`flow` 按发生顺序查看事件。Benchmark 仍然读取 `traces/`，因为 Trace 里有轮数、工具次数、Token 和最终任务状态等评测字段；会话 JSONL 用来解释“Agent 为什么走到这里”。

### 旧目录怎么处理

仓库里已经存在的旧 `.tasks`、`.team`、`.traces`、`.transcripts` 和 `logs/` 没有被自动删除，它们可能包含历史调试数据。新运行不会继续写入这些目录。确认新实现运行稳定后，再单独做一次“旧数据迁移或清理”，避免把历史数据和新数据混在一起。

## 十、会话事件字段和工具调用关联

### `thinking`

表示 Agent 开始第几轮模型调用。它不是模型的隐藏思维内容，只是一个进度标记，用来判断 Agent 是否一直在重复调用模型，以及某次工具调用发生在第几轮。

### `assistant_note`

表示模型在准备调用工具时返回的行动说明，例如“先读取配置文件，再修改入口”。它只在这一轮确实包含工具调用时记录。最终回答不再额外写一份 `assistant_note`，避免和 `final` 保存相同内容。

### `final`

表示本次用户请求已经返回了一段最终回复。`status=RESPONSE` 只说明对话轮次结束，不代表 Benchmark 任务一定成功；任务成功与否以 Trace 中的任务状态为准。如果最终回复和上一条中间说明完全相同，`final` 会写 `content_reused=true`，正文只保留在前面的 `assistant_note` 中。

### `tool_call` 和 `tool_result`

这两个事件都带有相同的 `call_id`。它来自模型返回的工具调用 ID，并且会继续写入发送给下一轮模型请求的 `tool_call_id`；Anthropic 请求会转换成它要求的 `tool_use_id`。如果兼容 Provider 没有返回 ID，Agent 会生成当前轮次内稳定的本地 ID，避免结果只能靠事件顺序匹配。

这次补充不仅用于日志展示，也为后续异步或并发工具调用留下了最小必要的关联字段。

本轮又补充了两层位置标记：`round_id` 表示一次“用户输入 -> Agent 完成回复”的完整来回；`step` 表示这一来回中的事件顺序。比如用户输入是第 1 步，某一轮思考、工具调用、工具结果和最终回复会继续递增。`thinking.turn` 仍然表示模型调用轮次，二者含义不同：`round_id` 跨越一次用户交互，`turn` 只统计这次交互内的模型调用。

## 十一、修复多行输入被提前提交

### 现象

在控制台直接粘贴一段包含换行的长问题时，Agent 可能只收到第一行，后续行继续留在 PowerShell 的输入队列中。用户看到的结果就是：第一行已经触发了 Agent，完整问题被拆成了多次输入。

### 原因

当前 REPL 使用 Python 标准库 `input()`。它的行为是“按 Enter 提交当前行”，并不知道用户是在逐行输入，还是一次性粘贴了多行文本。这个问题发生在 CLI 输入层，不是 Agent、Provider 或上下文压缩导致的。

### 方案

没有立即引入额外终端编辑库，而是增加显式的多行输入模式：

```text
你 > /paste
... > 第一行
... > 第二行
... > /end
```

`/multiline` 是同样功能的别名。只有单独输入 `/end` 后，CLI 才会把所有内容用换行拼接成一次 `agent.chat()` 调用。普通单行输入仍然直接按 Enter 提交。

### 为什么先用显式结束标记

终端层很难可靠判断“快速粘贴的换行”和“用户想立即提交的 Enter”。自动猜测可能吞掉下一条命令，或者让普通输入出现额外等待。显式结束标记虽然多一步，但行为确定、没有新依赖，也保留了单行输入的原有习惯。

### 使用和验证

```text
输入 /paste
粘贴多行问题
输入 /end
```

后续如果确实需要类似编辑器的多行体验，再单独评估 `prompt_toolkit` 等终端输入方案，并用真实 PowerShell 粘贴场景验证，不要仅凭模拟输入判断完成。

## 十二、将多行输入升级为可编辑输入框

### 为什么上一版方案还不够好

上一版用 `/paste` 和 `/end` 解决了提前提交问题，行为确定，也没有新增依赖。但它仍然不像正常聊天输入框：用户需要记住开始和结束命令，粘贴后不能在同一个输入区域里自由移动光标和修改内容。

### 本轮方案

接入 `prompt-toolkit` 的多行 Prompt：

- Enter：在当前输入中换行；
- `Alt+Enter`：提交整段内容；
- `Esc` 后按 Enter：作为 `Alt+Enter` 不可用时的替代方式；
- 支持多行粘贴、光标移动和输入历史。

普通输入和多行输入统一在同一个编辑缓冲区中，不再因为粘贴内容的第一处换行而提前调用 Agent。

### 兼容策略

`prompt-toolkit` 已加入 `requirements.txt` 和 `pyproject.toml`。如果运行环境尚未安装它，CLI 不会直接崩溃，而是回退到上一版 `/paste` + `/end` 模式。这样依赖安装失败时仍然可以使用 Agent，但完整输入框体验需要先执行：

```powershell
py -m pip install -r requirements.txt
```

### 当前验证边界

本地已验证 CLI 编译和无依赖回退路径。当前环境尚未安装 `prompt-toolkit`，因此真正的 PowerShell 粘贴、光标编辑和提交快捷键还需要在安装依赖后由负责人手动验证。

## 十三、修复控制台中间说明被截断

### 现象

第 11 轮的模型行动说明在 JSONL 中是完整的，但控制台只显示了前面一小段，用户看到的内容在 `reflection` 中间突然结束。看起来像 Agent 没有完整输出，实际上是 UI 主动截断了文本。

### 原因

`src/cli/ui.py` 原先对 `assistant_note` 做了两层处理：把换行替换为空格，并且只保留前 240 个字符：

```python
text[:240]
```

这会隐藏较长的行动说明，尤其是包含错误分析和下一步工具计划的内容。

### 修改

现在控制台保留完整文本和原始换行，按行输出。终端本身负责视觉换行，JSONL 仍然保留同样的完整内容。

这次没有修改 Agent 的思考内容，也没有把隐藏的模型内部思维额外暴露出来；修改的只是已有 `assistant_note` 的展示方式。

### 关于 `Ctrl+C`

本次最后的 `mvn spring-boot:run` 是前台服务启动命令，成功时会持续占用当前进程等待服务运行。用户手动按 `Ctrl+C` 后，Agent 还没收到工具结果，所以 JSONL 停在 `tool_call`，没有 `tool_result` 和 `final`。这不是记录器丢数据，而是当前取消路径没有写入“用户中断”事件。

后续如果要优化服务启动场景，应单独设计前台命令、后台命令和用户取消语义，不要简单把所有长命令都强行截断。

本轮已先补齐取消链路：`ShellSession` 捕获 `Ctrl+C` 后返回 `[用户中断]`，Agent 将工具结果标记为 `cancelled=true`，Trace 结束状态记为 `CANCELLED`，并继续写入最终回复。这样用户取消前台命令后，会话不会再停在没有结果的悬空 `tool_call`。

## 十四、区分输入阶段和工作阶段的 Ctrl+C

### 背景

之前 REPL 把“等待用户输入”和“Agent 正在工作”放在同一个异常处理分支里。无论用户是在编辑问题时按下 `Ctrl+C`，还是 Agent 正在请求模型、执行工具时按下 `Ctrl+C`，程序都会直接打印“再见”并退出。这容易因为误触导致整个会话关闭，也让用户无法只取消当前任务。

### 目标

把两种意图分开：

- 输入阶段按 `Ctrl+C`：认为用户可能想退出，先询问确认；输入 `y` 或 `yes` 才退出，其他输入和直接再次中断都回到输入提示。
- Agent 工作阶段按 `Ctrl+C`：只停止当前任务，记录取消事件，回到下一次用户输入，不退出 REPL。

### 修改

1. `src/cli/entrypoint.py` 将读取输入和调用 `agent.chat()` 分成两个异常边界。
2. 输入阶段新增退出确认；明确输入 `exit`/`quit` 仍然可以直接退出，因为这是主动输入的退出命令。
3. `src/agent/mini_claude_agent.py` 捕获模型请求或其他工具执行阶段冒泡出来的 `KeyboardInterrupt`，写入 `runtime_cancelled`，将 Trace 结束状态记为 `CANCELLED`，返回“已停止当前任务”。
4. `src/cli/ui.py` 增加清晰的任务停止提示。Shell 命令自身的中断路径继续沿用已有的工具结果记录逻辑。

### 为什么不统一成“按一次 Ctrl+C 就退出”

用户在长任务中按 `Ctrl+C` 的常见意图是停止当前操作，而不是丢弃整个会话。输入阶段没有正在执行的任务，才需要把 `Ctrl+C` 解释成退出意图，并增加一次确认来降低误触成本。

### 验证

- 退出确认只接受 `y`/`yes`，空输入默认不退出。
- 在输入框中按 `Ctrl+C` 后回答否，应该继续显示输入提示。
- Agent 执行长命令时按 `Ctrl+C`，应该看到任务停止提示并回到输入提示，JSONL 中应有 `runtime_cancelled`，Trace 状态应为 `CANCELLED`。
- 本地自动化测试覆盖退出确认的肯定、否定和再次中断分支。

### 当前边界

明确的 `exit`/`quit` 命令暂时不再额外询问确认，因为它本身已经是用户明确表达的退出动作。若后续发现误触退出命令也很常见，再单独增加确认，不和任务取消逻辑混在一起。
